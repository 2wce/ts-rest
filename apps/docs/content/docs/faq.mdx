## What is ts-restless?

ts-restless is a maintained fork of [ts-rest](https://github.com/ts-rest/ts-rest) for contract-first, end-to-end typed REST in TypeScript. It preserves upstream contributor credits and MIT licence notices, with its own `@ts-restless/*` packages and release history.

## What is the release status?

The first stable target is **4.0.0**, with interim `4.0.0-alpha.*` prereleases while compatibility fixes continue. New-scope packages are being prepared and are not published yet. See the [prerelease and migration guide](/ts-restless-migration) for the current status, intended installation commands and differences from upstream v3.

The major changes include validator-independent Standard Schema defaults and explicit legacy Zod compatibility. Read the [Standard Schema migration guide](/standard-schema-migration) before upgrading.

## Who maintains the fork?

The initial maintainer is [@2wce](https://github.com/2wce). The original ts-rest project and its contributors are credited in the repository; their historical adoption and maintenance statements describe that upstream project.

## How can I contribute?

Open an issue or pull request in [this repository](https://github.com/2wce/ts-rest). For a bug, include exact package, framework, validator and TypeScript versions plus a minimal reproduction. Use [private vulnerability reporting](https://github.com/2wce/ts-rest/security/advisories/new) for security reports.

## How does this compare to tRPC?

[tRPC](https://trpc.io/) derives its typed client from the server router. ts-restless defines a shared REST contract separately from its implementation, so clients and servers can depend on the contract package independently.

With ts-restless, define ordinary HTTP methods and paths such as `GET /posts/:id`, then consume them through typed client calls. The API remains usable by clients outside TypeScript. Choose the approach that fits your API consumers and deployment boundaries.

## Why is my TypeScript intellisense _slow_? 🐌

You'll need to enable `strict` in your `tsconfig.json`:

```json
  "compilerOptions": {
    ...
    "strict": true
  }
```

If you're using a monorepo, make sure this is applied at the `project` level. Example:

```
./apps/some-app/tsconfig.json
```

^ make sure `strict` is `true` here

If you cannot use `strict` entirely, you'll need to at least enable `strictNullChecks`.

This is required as part of [Zod](https://github.com/colinhacks/zod#requirements). See why [here](https://github.com/colinhacks/zod/issues/1750).

### It's **still quite slow**

If you've correctly enabled `strict` and `strictNullChecks`, and you're still experiencing slow intellisense, you may be approaching the point at which (pre `tsgo`) Typescript
starts to feel fairly sluggish.

1. **Try split up your clients/contracts** We've had some success with _splitting up our clients_ into different domains, for instance `postClient`, `userClient`, `authClient` etc. this splits up the client into smaller chunks, which can help with intellisense performance.
2. **Move to a more tsc friendly validator** Zod 3 was fairly renowned for it's affect on intellisense in large codebases, [Zod 4](https://zod.dev/v4) improves greatly on this, and works through Standard Schema in the fork's unreleased major version. See the [migration guide](/standard-schema-migration) for the compatibility boundary.
3. **Utilise monorepo tooling** - NX (and probably others) offers some ways to pre-compile modules, emitting .d.ts files for your modules, this could be a good way to speed up intellisense.
